# AGENTS.md

Lazarus / Free Pascal markdown editor/viewer (MDPad). Cross-platform via `{$IFDEF MSWINDOWS}`. No tests, no CI, no lint.

## Build

- `lazbuild MarkDownPad.lpi` (modes `Default`/`Debug`/`Release`). Toolchain here: fpcupdeluxe install (`~/fpcupdeluxe/lazarus/lazbuild --pcp=~/fpcupdeluxe/config_lazarus`), FPC 3.3.1 trunk + Lazarus 5.99 — the old system Lazarus is gone, use this one.
- Syntax mode `Delphi` with `-dBorland -dVer150 -dDelphi7 -dCompiler6_Up -dPUREPASCAL` (in `.lpi`, don't override). Unit output `lib/$(TargetCPU)-$(TargetOS)`; `PathDelim` is `/` — keep it.
- Required packages (in `.lpi`): `LCL`, `atsynedit_package` + `atsynedit_ex_package` + `econtrol_package` (editor + EControl adapter/lexers), `FrameViewer09` (THtmlViewer), `printer4lazarus`, `MyWiki` (converters in `../components/WikiConverter/MyWiki`, registered via `--add-package-link`, NOT via `OtherUnitFiles` — base `SearchPaths` don't propagate into build modes, so raw paths silently break the build), `markdown4d_lcl` (`~/projects/Markdown4D/packages/markdown4d_lcl.lpk`, see *Third preview backend* below).
- Widgetset: default gtk2 needs system gtk2 (`sudo pacman -S gtk2`, not installed here) or linking fails on `-lgtk-x11-2.0`. **Verified path: `lazbuild --ws=qt6 MarkDownPad.lpi`** (LCL-qt6 units + `libQt6Pas.so.6` ship with this Lazarus; no qt5 bindings, so `--ws=qt5` won't link). Headless smoke test: `QT_QPA_PLATFORM=offscreen ./lib/x86_64-linux/MarkDownPad ./markdowntest.md` (clean exit, writes `settings.ini` next to the binary).
- Lowercase unit filenames are mandatory (`markdownprocessor.pas`, not `MarkdownProcessor.pas`) — FPC lowercases unit names when searching on case-sensitive filesystems. Keep the `Unit` identifiers as-is.
- `{$R *.res}` is guarded to `{$IFDEF MSWINDOWS}` in `.lpr` (Delphi-origin icon/manifest resource).
- `lib.lxl` (EControl lexers: the markdown highlighting) is loaded from the **exe dir** at startup; without it the editor silently falls back to plain text. Its Markdown lexer declares **no tree rules** (`TreeGroup`/`DisplayInTree` are set only by its Bash/C/PHP lexers), so EControl's code tree stays empty for a markdown document: MDPad fills the `Tree` as the table of contents itself (see *Editor*). `tools/copy-lexlib.sh` copies it from `$ATSYNEDIT_DIR/app/lexlib/` (default `~/projects/components/ATSynEdit`) into every `lib/<cpu>-<os>/` output dir *and* the project root (where Release writes its binary), and is wired as the `.lpi` *Execute after* command in all three build modes (Lazarus/lazbuild run it with cwd = project dir; the script never fails the build — a missing source just prints a note). `lib.lxl` is git-ignored.

## Linux release artifacts (`tools/build-release.sh`)

- `./tools/build-release.sh` builds the release (`lazbuild --ws=gtk3 --build-mode=Release`) and writes versioned artifacts to `dist/` (git-ignored): `mdpad-<ver>-linux-x86_64.tar.gz` (portable folder, also the payload of the other formats), `mdpad_<ver>_amd64.deb`, `mdpad-bin-<ver>-1-x86_64.pkg.tar.zst` (when `makepkg` exists) plus `dist/arch/{PKGBUILD,.SRCINFO}` for the AUR, `mdpad-<ver>-x86_64.AppImage`, `dist/flatpak/io.github.vhanla.MDPad.yml` (Flathub-ready manifest; a `.flatpak` bundle too when `flatpak-builder` exists) and `dist/SHA256SUMS`. Flags: `--version X.Y.Z` (default: the `VERSION` file), `--formats tar,deb,arch,appimage,flatpak`, `--no-build` (package the binary already in the project root), `--ws`, `--keep`. Missing tools skip only their format and say so.
- **Version**: `VERSION` (tracked, `1.3.7`) is the release's version and must match `ABOUTMDPAD` in `pagedown.inc`, which is what the About box shows; bump both together. The tarball embeds the version in its top folder name, so `--version` alone is enough for a different number on the artifact, but the About box would still show the old one.
- **gtk3, not qt6, for releases**: a GTK3 binary needs only `libgtk-3` (every desktop distribution, and the GNOME Flatpak runtime, ship it) and no Lazarus-specific library, so nothing extra travels with the package. `--ws qt6` still works for local testing: the script detects the linked widgetset with `readelf` (and rebuilds once with `-B` if lazbuild kept an incremental build), bundles `libQt6Pas.so.6` next to the binary (the wrappers put that folder first in `LD_LIBRARY_PATH`), adds Qt6 dependencies to the deb, and skips Flatpak (the GNOME runtime has no Qt6).
- **Payload layout**: the app reads `lib.lxl`, `Theme.json`, `style.css` and `Readme.md` from `ExtractFilePath(ParamStr(0))`, so the binary never goes to `/usr/bin` alone. The deb/Arch package install it as `/usr/lib/mdpad/mdpad` and `/usr/bin/mdpad` is a two-line wrapper that `exec`s it (argv[0] is then the real path); the AppImage's `AppRun` and the Flatpak's `/app/bin/mdpad` do the same for their `usr/lib/mdpad` / `/app/lib/mdpad`. The tarball is the portable case: the binary sits at the top of the folder and the files are next to it.
- **`settings.ini` location** (this is what makes system installs work at all): `SettingsFileName` keeps the old behaviour — next to the binary — while that directory (or the existing file) is writable, and otherwise uses `$XDG_CONFIG_HOME/mdpad/settings.ini` (`~/.config/mdpad/`), creating the folder. Without it `TIniFile.Create` cannot even create the file in `/usr/lib/mdpad`, a read-only AppImage mount or a Flatpak sandbox, so the app would fail at startup. Verified both ways: a writable folder keeps the ini beside the exe, a `chmod a-w` folder (and a missing ini) sends it to `$XDG_CONFIG_HOME/mdpad/`. `Readme.md`, `Theme.json`, `style.css`, `lib.lxl` stay exe-relative (read-only is fine).
- **Packaging assets**: `packaging/io.github.vhanla.MDPad.desktop` (app id doubles as the Flatpak id), `packaging/io.github.vhanla.MDPad.metainfo.xml.in` (`@VERSION@`/`@DATE@` filled in by the script; `appstreamcli validate` clean, `desktop-file-validate` clean) and `packaging/icons/hicolor/<size>/apps/mdpad.png` (16…256, extracted from `MarkDownPad.ico`'s 256px frame).
- **Reproducible**: the tarball is built with `tar --sort=name --mtime=@$SOURCE_DATE_EPOCH` + `gzip -n`, the deb's tars with the same `--mtime` and `ar rcsD`; `SOURCE_DATE_EPOCH` defaults to the last commit's time. Two runs of the same commit produce byte-identical tarball, deb and AppImage (verified with `sha256sum`), so the hashes baked into the PKGBUILD and the Flatpak manifest stay valid. The AppImage is a type-2 runtime + `mksquashfs -comp xz` (the continuous runtime supports only xz/zlib, not zstd) — `<runtime> + <squashfs>`, no FUSE needed to build; the runtime is downloaded once into `dist/.cache/`.
- **Verified here**: the Release gtk3 build; tarball, deb, Arch package and AppImage contents; the app started from the tarball, from the extracted deb payload (`/usr/lib/mdpad`, read-only) and from the extracted AppImage (`./squashfs-root/AppRun`); `pacman -Qlp`/`-Qip` on the Arch package; `desktop-file-validate`, `appstreamcli validate`; hash stability across two runs. **Not verified**: installing the deb/Arch package on a real Debian/Arch system (`dpkg-deb` and `rpm` are not on this box, so the deb was assembled with `ar`+`tar` — the documented member order — and only inspected, not installed), a real Flatpak build/install (`flatpak-builder` is not installed; only the manifest is produced and YAML-checked), and the AUR package against the published GitHub asset (the local build used the tarball sitting next to the PKGBUILD; the source URL and its sha256 match the released file byte for byte).

## Architecture: the preview backends

- **`SelectedPreview`** picks the *backend* (which control renders); **`SelectedEngine`** picks the markdown→HTML *engine*. They are separate axes; persisted as `preview=` / `engine=` in `settings.ini`, switched from *View → Preview: …* (`TogglePreview`) and *Engines* (`ToggleEngine`) respectively. Both handlers write the file **at the moment of the pick** (`SaveINI`; the save in `FormDestroy` is too late if the process is killed, crashes, or hangs on a worker) — it also runs first in `FormDestroy` for the same reason — and `LoadINI` falls back to `pvHTML`/`mdNATIVE` for a value this build does not know (a `settings.ini` from another build or from Windows), so the last picked pair is what the next start opens with. The rest of the *View* toggles that are persisted do the same (`Synceditwithpreview1Click`, `Waitafewsecondsbeforeupdatingthepreview1Click`, `Statusbar2Click`, `mnuViewTreeClick`, `Loadremoteimages1Click`); the ones that are not persisted at all are session state and stay that way: the editor/result layout (`EditorandResult1`/`Editoronly1`/`Resultonly1`), fullscreen, and the canvas viewer's own Ctrl+wheel zoom (which never reaches `TrackBar1` — see *Third preview backend*).
  - `pvHTML` (default): `THtmlViewer` (`PreviewHtml`, created in `FormCreate`), always paired with the **native** engine (`TMarkdownProcessor`, default `SelectedEngine = mdNATIVE`). No JavaScript: `UpdateResult` renders to string and calls `LoadFromString` synchronously (no `DocumentComplete` dance).
  - `pvMARKDOWN4D`: `TMarkdownViewer` (`PreviewMd4D`, canvas renderer, parses the markdown itself — no HTML, no MyWiki). `UpdateResult` hands the source straight to it; `UsingMarkdown4D` gates every path that differs (scroll sync, zoom, print, Export HTML).
  - `pvIE`: legacy ActiveX `TWebBrowser`, **only** under `{$IFDEF MSWINDOWS}`. Picking one of the 5 JavaScript engines (PageDown, MarkdownJS, Marked, ShowDown, MarkdownIt) forces this backend regardless of `SelectedPreview` (that is what `UsingIE` checks).
- `UsingIE` / `UsingMarkdown4D` / `ActivePreview` decide the control on duty; `ApplyViewMode` hides all of them and re-applies editor/result layout after any backend switch. Add new backends to all four.
- The panes sit left to right as **tree | Splitter2 | editor | Splitter1 | viewer**: the tree is the table of contents (`.lfm`, `alLeft`), `Splitter2` divides it from the editor, `Splitter1` divides the editor from the viewer, and the viewer is the `alClient` control that takes the rest (`PreviewHtml` / `PreviewMd4D` / `BrowserContainer`). *View → Table of contents* (`mnuViewTree`, `[MDPad] tree`, default on, saved on the pick like the other View toggles) hides the tree **and** `Splitter2` (`Visible`, inside one `DisableAlign`/`EnableAlign` around `ArrangePanes`, so the editor moves to `Left` 0 and the viewer — `alClient` — absorbs the freed `Tree.Width` + 5 px; the tree keeps its own width for when it comes back). While it is hidden nothing fills it: `UpdateTOC`, `AdapterParseDone`'s EControl `TreeFill` and the `CodetreeSelectItemForPosition` walk of `EditorChangeCaretPos` all bail out on `FTreeVisible`, so a render or a caret move no longer costs the tree; `RefreshTree` builds the contents once when it is shown again (the markdown TOC through `UpdateTOC`, EControl's tree for the other lexers through `TreeFill` off the still-current parse data), and if the headings did not change meanwhile the existing nodes are kept. Measured with a temporary probe: both = `tree 0:121, split2 121, editor 126:791, split1 917, viewer 922:660`; hidden = `editor 0:791, split1 791, viewer 796:786`; shown again restores the first numbers exactly, and a render while hidden leaves the old 2-node tree in place while `FHeaders` already holds the new 3 headings — which the show then builds (`tree=3 [One][Two][Three]`). Live splitters: `Splitter2` resizes `Tree` and `Splitter1` resizes `BCEditor1` (both `TSplitter.FindAlignControl` = the nearest control to its left; the viewer absorbs the change) — verified by calling the two `FindAlignControl`s under gdb, not by dragging (X input does not reach the Qt window on this box). LCL lays `alLeft` controls out from left to right in the order of their **current `Left`**, so `ArrangePanes` writes the four lefts in that order and each view-mode handler (`EditorandResult1Click` / `Editoronly1Click` / `Resultonly1Click`) does its visibility/align/width changes and calls it inside one `DisableAlign`/`EnableAlign` pair, so a single align pass (through `EnableAlign` → `DoAllAutoSize`) sees the finished state. Without it the editor — created at runtime with `Left` 0 — was laid out before the tree and came out leftmost. In the single-pane modes the tree and `Splitter2` stay, and `Splitter1` is **hidden** (not merely disabled: `Enabled` leaves it in the layout and it would eat 5 px and sort in wherever its stale `Left` falls) — measured geometry: both = `tree 0:121, split2 121, editor 126:600, split1 726, html 731:469`; editor only = `editor 126:1074, split1 hidden`; result only = `html 126:1074, split1 hidden`; switching back restores the both-mode numbers, and the canvas backend lands exactly where the HTML one does (`canvas 581:319` after a resize to 900). The editor and viewer keep the widths they had before the fix (only the tree moved from the middle to the left), so the HTML anchor table and the scroll sync see the same preview geometry as before.
- Windows-only units (`Windows`, `ActiveXContainer`, `MSHTML_*`, `SHDocVw_*`) and APIs (`registry`, `CoInternetSetFeatureEnabled`, `SetPriorityClass`, `keybd_event`, `GetAsyncKeyState`, `ReleaseCapture/Perform`) are all behind `{$IFDEF MSWINDOWS}`. Never reference `Browser`/`BrowserContainer` outside such a guard.
- `LazActiveX` was dropped from `RequiredPackages` (doesn't compile on Linux). Windows builds need it installed in the IDE for the IE path; the IDE auto-suggests adding the dependency.
- `ExceptionLogger` was dropped (unused by our code, and its OPM copy fails to build on Linux: missing `dcconvertencoding.inc`).

### Engines (`SelectedEngine`: markdown → HTML)

- `mdNATIVE` (6, default): MyWiki's `TMarkdownConverter` (`WikiToHtml`), run in `TConversionThread`. It also fills the header list.
- `mdMARKDOWN4D` (7, *Engines → Native GFM (Markdown4D)*): Markdown4D's **Core** — a second native (pure Pascal, no browser, no MyWiki) implementation, same worker thread. Its Core is plain Pascal, so calling it off the main thread is fine. It renders through **MDPad's own pipeline** (`Md4dPipeline`: the builders `TMarkdown.ToUnsafeHtml` uses, plus `HeadingAnchors`) because the shared pipelines leave the headings unnamed — the conformance corpora compare their output byte for byte — while a preview wants an id to send the reader to; `HeadingAnchors` writes the anchor `TMarkdownToc` knows a heading by as the id of its element, so the ids in the HTML and the outline entries cannot drift. The worker also parses the document once more (`Pipeline.Parse`) to hand `FHeaders` over (line = `SourceLine - 1`), so this engine fills the table of contents and the HTML anchors exactly like the native one; `PreviewHtmlBody` (Export HTML while the canvas backend is on) renders through the same pipeline, so the exported page is the page that was on screen (and its in-page links resolve). `UnsafeHtml` (not `ToHtml`) on purpose: it keeps raw HTML, which is what MyWiki and the JS engines do and what the canvas lays out (`HtmlBlock`), and `markdowntest.md` is mostly raw HTML.
- `mdPAGEDOWN`…`mdMARKDOWNIT` (1–5): JavaScript, so on Windows they force the IE backend (`UsingJsEngine`) whatever `SelectedPreview` says; off Windows they fall through to the native path.
- `ToUnsafeHtml`, **not** `ToHtml`, on purpose: it keeps raw HTML, which is what MyWiki and the JS engines do *and* what the Markdown4D canvas draws (its layout engine lays out `HtmlBlock` nodes). The GFM **tag filter** stays on either way, so `<script>/<style>/<iframe>/<title>/<textarea>/…` get escaped — the exact list MyWiki escapes (`RegexDisallowdRawHtml`). `ToHtml` would instead drop every raw HTML block, and since `markdowntest.md` is mostly raw HTML the preview would lose most of its content. `PreviewHtmlBody` (Export HTML while the canvas backend is on) uses the same mode so the exported page matches the canvas.
- `markdownprocessor.pas` (Delphi's `TMarkdownProcessor`) is still in the `uses` clause and the `.lpi` but is **never called** — the native engine has always been MyWiki. Left alone.

### Third preview backend: Markdown4D (`pvMARKDOWN4D`)

- `~/projects/Markdown4D` is a CommonMark/GFM parser + **canvas** renderer (no browser). Its FPC/LCL port (`Source/Lcl`, targeted at FPC 3.3.1 + Lazarus trunk — the same toolchain as here) provides `TMarkdownViewer` in package `markdown4d_lcl`.
- The package depends on the **generated** tree: `build/fpc/{Core,Layout,Fpc,Lcl}` and `packages/markdown4d_lcl.lpk` are produced by `tools/fpcport/makefpc.sh` (Python transformer) and are *not* checked in. Regenerate before building MDPad on a fresh checkout, then link it **with the same widgetset**:
  - `tools/fpcport/makefpc.sh` (in `~/projects/Markdown4D`)
  - `lazbuild --pcp=~/fpcupdeluxe/config_lazarus --ws=qt6 --add-package-link ~/projects/Markdown4D/packages/markdown4d_lcl.lpk`
  - Omitting `--ws=qt6` registers the link for gtk3 and the qt6 build then says `Broken dependency`.
- Two generator bugs had to be fixed in `tools/fpcport/makelpkg.py` (both break the package silently):
  - the `.lpk` **file name must equal the package name** (`markdown4d_lcl.lpk`, not `Markdown4D.Lcl.lpk`) — `TPackageLink.IsMakingSense` in `packagelinkintf.pas` requires it, otherwise `--add-package-link` silently drops the link;
  - it must emit `<UsageOptions><UnitPath Value="$(PkgOutDir)"/></UsageOptions>`, otherwise a project that requires the package gets no unit path and fails with `Can't find unit Markdown4D`.
- Two more in `tools/fpcport/porttree.py`, both about `Source/` vs the port:
  - the `pristine` copy of `Source/` that each round starts from was only taken `if not keeper.exists()`, so **edits to `Source/` after the first generation were silently ignored** (the tree kept being rebuilt from the stale snapshot). It now refreshes whenever the file differs;
  - `Source/Lcl/` is copied **verbatim** (not transformed), so it must be valid FPC as written: `for var X in ...` is a syntax error there. The Core/Layout rewrite that ports inline declarations away does not run on the LCL layer.
- **Never cast the painter with `as`, and never `Free` it while an interface reference exists.** FPC's interface table carries only the interface the class declares, not its ancestors, so `Painter as ITextMeasurer` raises `EInvalidCast` at run time (the class declares `IPainter`, which *descends* from `ITextMeasurer`; `Painter as IPainter` happens to work, the ancestor cast does not). Declaring `PainterLifetime: IPainter` and assigning `PainterLifetime := Painter` compiles and works, because passing an `IPainter` value where an `ITextMeasurer` is expected is a plain upcast with no `QueryInterface` (this is exactly what `TMarkdownViewer.Paint` does with `FMeasurePainterLifetime`). Also note FPC rejects `ITextMeasurer(Painter)` and the implicit `M := Painter` *to the ancestor* at compile time. Two more traps measured on FPC 3.3.1 (see the scratch tests: `Painter as IFoo` takes **two** refs and releasing the variable gives back one, so it leaks; and `TInterfacedObject.Free` on an object whose refcount is not 0 raises `EInvalidPointer`). Hence: the interface reference **owns** the painter — release it by clearing `PainterLifetime` (clear the class-typed variable first), never with `Painter.Free`. The old `Painter as IPainter` + `Painter.Free` pair crashed on both counts.
- Code/ASCII-art alignment: Markdown4D's default theme asks for `Consolas`, and its family resolver used to rewrite any missing family to the proportional UI font (`Segoe UI`) — off Windows that made code blocks proportional, so columns and box-drawing shifted per row. Fixed in the library (`TMarkdownViewerShared.IsMonospaceFamilyName` + `MonospaceFamilyCandidates`, probed by `LookupFamilyName` in the LCL and VCL painters); MDPad needs no change and the editor's own font (`Consolas` → whatever the widgetset substitutes) may still differ slightly from the preview's (on this box: DejaVu Sans Mono). Verify with a measurement, not by eye: a monospace font gives `MeasureText('MMMM') == MeasureText('iiii')`; `MMMM=58 / iiii=16` means proportional.
- Integration notes: the viewer owns an incrementally-reparsed model and marshals `SetText` to the main thread (`InvokeOnMainThread`), so there is **no worker thread** in this path. `OnLinkClick` only sees external targets (in-page anchors are resolved by the viewer). Scroll sync uses the exact `SourceLineToScrollOffset` (not the caret-line ratio), zoom maps to the viewer's real `Zoom` (the `TrackBar1` ladder, 50–200% through `ZoomPct`, *and* the viewer's own Ctrl+wheel ladder, 25–500%; the two do not track each other — the trackbar re-applies its value when moved, a Ctrl+wheel step leaves the slider stale, and the model re-anchors the top line itself), and print renders the display list through `TMarkdownLclPainter` onto page bitmaps (`Printer.YDPI` is FPC's property; there is no `PixelsPerInch`). `<bitmap>.SetSize` must happen *before* the painter is created (resizing afterwards resets the canvas font behind the painter's applied-font cache).
- Zooming the canvas rescales the theme through `SaveToJson`/`LoadFromJson` (`TMarkdownTheme.Scaled`), so every color crosses JSON text: on FPC that used to die with `"4280230696" is an invalid integer` (vcl-compat's `TJSONNumber.AsInt64` parses with the 32-bit `StrToInt` wherever `Char` is one byte) until the port's `JsonAsInt64` — see *Compiler and vcl-compat divergences* in `~/projects/Markdown4D/docs/FPC.md`. The library is a package dependency, so a stale `packages/lib/x86_64-linux` keeps the crash alive; regenerate with `tools/fpcport/makefpc.sh` first.
- The viewer fetches remote images on `TTask`, so **`cthreads` must be first in the `.lpr` on Unix** (already the case).
- **Images**: the viewer resolves `<img src>` itself: `Images.BaseUrl` (folder or server) wins, then the folder `LoadFromFile` recorded (`Text :=` never sets it), and with neither a relative source is handed to the file system as written — i.e. relative to the process CWD. MDPad calls `ApplyPreviewBaseFolder` (from `UpdateResult`), which points `PreviewMd4D.Images.BaseUrl` **and** `PreviewHtml.Base` at `ExtractFileDir(CurrentFile)`; `Base` is THtmlViewer's lever for the same thing (the HTML preview never fetches http(s) images, only the canvas one does). Verified under gdb with a red `img.bmp` in the CWD and a blue one next to the document: `TMarkdownViewer.LoadLocalImage` and `THtmlViewer.HtmlExpandFilename` both name the document's folder.
- Remote images (canvas backend only) are fetched by the library on its own `TTask` workers (4 at a time, redirects, timeouts, `MaxBytes` = 8 MB, completion marshalled to the main thread) — MDPad needs no download thread and no locking. *View → Load remote images (canvas preview)* toggles `Images.AllowRemote` (persisted as `remoteimages`, default true) and then calls `ReloadImages`, because an image refused under the old setting sits in a *failed* slot that is never retried by itself. Verified end to end against a local HTTP server: `remoteimages=0` leaves no request in its log, `1` (and absent) makes one.
- Library image state is per viewer instance: slots keyed by the **raw source** (`Requested/Loaded/Failed`), the decoded graphics, and an in-flight dedupe set. There is **no disk cache anywhere**, and the FPC HTTP shim (`Markdown4D/Source/Fpc/System.Net.HttpClient.pas`) exposes only `Get` — no request headers, no `HEAD` — so `If-None-Match`/`If-Modified-Since` revalidation cannot be done from the app; a persistent cache belongs in the library. What this round added there: a change of `BaseUrl`/document folder drops the sources that resolve against it (relative ones), so a same-named image from another document can no longer stay on screen, and `ReloadImages` forgets every image and asks for them again (retry a failure, pick up a file that changed on disk).

### Theming and the Preferences menu

- `SelectedTheme` (`TAppTheme = (atSYSTEM, atLIGHT, atDARK, atCUSTOM)`) is a third axis next to the backend and the engine, persisted as `theme=system|light|dark|custom`. It is picked from *Preferences → Theme → System/Light/Dark/Custom* (`mnuThemeSystem/Light/Dark/Custom`, all `OnClick = mnuThemeSelect`, the item `Tag` **is** the enum value) or through *Enable Syntax highlighter* (`mnuSyntax`) and *Enable Custom Style (style.css)* (`mnuCSS`). All three handlers `SaveINI` **at the moment of the pick**, like `TogglePreview`/`ToggleEngine`. `LoadINI` maps a settings.ini from an older build (only the `themeenabled` boolean) to `custom` when it was on and `system` otherwise, and defaults `syntaxenabled` to true.
- `ApplyTheme(AReloadPreview)` paints every surface in one place and is idempotent: editor palette (`SetEditorPalette`: light/dark `TATEditorColors` built from `Colors.Init`), EControl token colors (`SetLexerPalette`), chrome (`ApplyChromeColors`: form, tree, both splitters, status bar — LCL menus belong to the widgetset and stay light), canvas (`ApplyCanvasTheme`), the previews' sheet (`RefreshPreviewStyle`) and the menu marks (`UpdateThemeInMenu`); then `InvalidateHtmlAnchors` + `InvalidateScrollSync` and, when `AReloadPreview`, a re-render (`UpdateResult` for the native HTML preview, `LoadEngine` + `ReloadingEngine` for the IE path; the canvas needs nothing, `SetTheme` already re-lays out and invalidates). `FormCreate` calls it with `False` right after `LoadINI`.
- The token palette is **Markdown4D's**: `SetLexerPalette` maps that theme's `TokenColors[TSyntaxTokenKind]` (via `ArgbToLclColor`, since its palette is `$AARRGGBB` and `TColor` is `$00BBGGRR`) onto EControl format names, so the editor's code and the canvas color the same tokens the same way. It writes **every** background (`clNone` where the token has none) because lib.lxl ships light pastel backgrounds that would otherwise survive into dark mode, and it names the Markdown lexer's own 17 formats (`Heading`, `Comment`, `Quote`, `Text`, `Codeblock`/`Block`, `Link`, `Image`, `Reference`, `Footnote`, `HTML Code`, `Bold`, `Italic`, `Bold-Italic`, `Definition`, `List`, `Crossed out`) plus the generic ones the embedded lexers use (`String`, `Number`, `Reserved word`, `Preprocessor`, `Identifier`, `Comment 1…`). Mutating a `TecSyntaxFormat`'s `Font.Color`/`BgColor` repaints without a reparse, which is why a theme switch is instant.
- The custom theme is the app's own files, no new format: `Theme.json` (BCEditor's theme file, the one MDPad always shipped) paints the editor (`Colors/Editor/Colors` keys → `TATEditorColors` through `ApplyEditorOverrides`) and its `Elements[]` (BCEditor element names → EControl formats through `EcontrolNamesForTheme`/`ApplyLexerOverrides`); the **luminance of `Colors/Editor/Colors/Background` decides whether the rest of the app is painted light or dark**, so the editor and the previews cannot disagree (a light Theme.json flips the previews to light too — verified with both). `style.css` rides on top of the HTML preview's sheet when "Enable Custom Style" is on; `Md4dTheme.json` (a theme exported with Markdown4D's `Theme.SaveToJson`) is loaded into the canvas when Custom is picked and the file exists, else the Light/Dark preset matching the above. `ApplyCanvasTheme` **always builds and owns the theme** — preset or `Md4dTheme.json` — and assigns it through `PreviewMd4D.Theme`: `SetTheme` only *borrows* what it is given, which is what lets MDPad set `CodeFont` on the object before the viewer sees it (a theme property would have to be re-applied to take effect, and `SetThemePreset` frees only the presets it created itself). `FCanvasTheme` is freed in `FormDestroy`, after the viewer, and again right after each switch.
- Code blocks in the preview draw with **the editor's font** when that is a monospace one (`EditorCodeFontName`), so a code block in the editor and in the preview line up the same way. The name check is Markdown4D's own (`TMarkdownViewerShared.IsMonospaceFamilyName`, the `MonospaceFamilyCandidates` list) so a family that is merely not installed here (`Consolas` off Windows) still counts: both consumers fall back to an installed monospace face, while an unknown family is measured instead (`MMMM` vs `iiii` on a bitmap canvas) and pinned only if it really is monospace — a proportional editor font must not be forced on code. It lands in the HTML sheet as `code,pre,kbd,samp,.md code,.md pre{font-family:"<name>",monospace;}` appended after the theme (so it wins by order) and **before** `style.css` (so that file can still override it), and in the canvas as `Theme.CodeFont.FamilyName`. Picking a font (`Editor → Font…` or the Options dialog) re-applies the theme (`ApplyTheme(True)`), which is what rewrites both.
- The previews' CSS is in `pagedown.inc`: `HTMLCSSLIGHT` and `HTMLCSSDARK` replace the old `CSS`/`GITHUBCSS`/`DEFAULTTHEME` consts. Both are `'<style type="text/css">' + …` chains **without** the closing tags; `RefreshPreviewStyle` composes `PreviewCSS` (sheet + `style.css` when enabled + `</style></head>` — the JS engines' `HEADER` opens the head) and `PreviewHtmlHead` (doctype + head + `<body>`, used by the worker's `SyncUpdateUI`, by `LoadEngine` and by **Export HTML**, where `PreviewCSS` replaces the old `CSS`). An unknown `theme=` value (a settings.ini from another build) resolves to `system`.
- System detection has no LCL API, so `SystemPrefersDark` reads the Windows registry (`AppsUseLightTheme`), macOS (`defaults read -g AppleInterfaceStyle`), Linux (`GTK_THEME`, then `gsettings … color-scheme|gtk-theme`) through `TProcess` (`RunHelper`); no answer at all means Light. On this box `color-scheme` is `prefer-dark`, so System resolves to Dark (verified); a desktop that answers nothing falls back to Light.

### Recent files and the Editor menu

- The MRU list is `FMRU: TStringList` + `FMRULimit` on `TForm1` (limit 1..30, default 10), persisted as `[Files] mrucount` + `mru0..mruN` (newest first; the keys a shortened list no longer has are deleted on save). `File → Open recent` (`mnuRecent`) is declared in the `.lfm`, its children are built at run time by `RebuildRecentMenu` (`Clear` frees them — LCL's `TMenuItem.Clear` destroys children, `Delete` does not); a file item's `Tag` is its index, `AddToMRU` moves a path to the top, drops duplicates and calls `SaveINI` **at the moment of the open**. `mnuRecentClick` checks `FileExists` first (a missing file warns and drops the entry), then goes through `CanOpenAnotherFile` — the save/discard/cancel prompt extracted from `Open1Click` (a cancelled Save-as cancels the open by re-checking `textBuffer = BCEditor1.Text`) — before `OpenMDFile`. `File → Clear list` empties menu and list.
- `AddToMRU` is called wherever a document is really opened: `Open1Click`, the command-line open, `Saveas1Click` (a new file becomes recent once it has a name) and the IE `DocumentComplete` path; the bundled Readme opened on first start deliberately does not enter the list.
- The `Editor` menu is the quick-toggle half of the options, and it shares their state instead of copying it: `Gutter`, `Ruler`, `Minimap`, `Unprintable characters`, `Word wrap`, `Formatting bar`, `Continue lists on Enter` (`Tag` 0..6, all `OnClick = mnuEditorToggleClick`) flip the field in `FEditorOpts`, then `ApplyEditorOptions` + `UpdateEditorMenuChecks` + `SaveINI`. `Format → Wordwrap` calls the same handler: it used to toggle `OptWrapIndented` (the indent of *wrapped* lines), so with wrapping off by default it looked dead. `Editor → Font...` reuses `Font1Click`, which now stores the pick in the record (the old code forced Consolas on every start, so a chosen font never survived).

A non-markdown file (or no file) keeps the menu's own default. `--view=...` always wins, including for a non-markdown path. The old Windows IE path forced `Resultonly1Click` in `WebBrowser1DocumentComplete`; it now just re-applies `ApplyViewMode`, so `--view=both` survives there too.

### Markdown editing: commands, format bar, Smart Enter, completion

- Two new units: `mdformat.pas` is the text engine (no window, no LCL, testable headless) and `mddialogs.pas` holds the three runtime insert dialogs (LCL, but self-contained). The engine speaks the editor's units: offsets in UTF-16 code units, 0-based, `End` exclusive, and returns a `TMdEdit` (`Changed`, `StartOffset`/`EndOffset`, `InsertText`, `SelStart`/`SelEnd`) instead of touching anything. It deliberately avoids `Trim`, `StringReplace`, `StrToIntDef`, `WideCompareText`, `sLineBreak` and `TStringList`: the first four drag in implicit Unicode↔Ansi conversions or the widestring manager, `sLineBreak` *is* an AnsiString, and a `TStringList` in a German/Japanese Windows codepage would mangle the collected words (it uses `TMdStringArray`, `MdTrim`, `MdIntToStr`, `MdCompareTextI`, `MdEqualText`, `MdStartsWithText`, and LF as the no-EOL fallback).
- Engine surface: `MdToggleInline` (`**`, `*`, `~~`, `` ` `` — wraps/unwraps the selection, or the word under the caret, or inserts the pair and leaves the caret between the markers; a marker that is part of a longer run of the same character is not that marker, so Ctrl+I inside `**bold**` gives `***bold***` instead of stripping the bold), `MdToggleLinePrefix` (`> `, `- `, `1. ` — adds to every selected line, or removes from every line that has it), `MdCycleHeading` (`#`→`##`…→no heading), `MdToggleTask` (`- [ ]`↔`- [x]`), `MdToggleFence`, `MdInsertTable`/`MdInsertRule`, `MdInsertLink`/`MdInsertImage` (plus `MdBuildLink`/`MdBuildImage` for the dialogs, so editing an existing link rebuilds it instead of nesting brackets, and `MdFindMarkupAt`, which finds the link/image the caret is in or touching and parses back text/target/title — including the `<url>` and `"title"` forms), `MdContinuation`, `MdWordBeforeCaret`/`MdCollectWords`.
- One dispatcher: `TMdCommand` (`mcBold`…`mcCompleteWord`) and `MdExecute`; the enum value travels in the `Tag` of every context-menu item and every format-bar button (`MdCommandClick` reads it) and the keys call `MdExecute` directly, so the three cannot drift apart. `ApplyMdEdit` is the only writer: one undo group (`Strings.BeginUndoGroup` … `EndUndoGroup`) around `DoCommand(cCommand_TextDeleteSelection, TATCommandInvoke.Internal)` + `TextInsertAtCarets`, then the selection the engine asked for via `Carets[0].Change` + `SelectNone` + `DoShowPos`; one user command undoes as one step (verified).
- Keys live in `BCEditor1KeyDown`, which sets `Key := 0`: the user's `OnKeyDown` runs *before* LCL's shortcut dispatch, and the popup menu's `ShortCut`s are only display hints (the editor's popup is checked by `IsShortCut` after it), so the shortcut shown next to a menu item and the handler can never both fire. Ctrl+B bold, Ctrl+I italic, Ctrl+Shift+X strike, Ctrl+`` ` `` inline code, Ctrl+K link, Ctrl+Shift+K code block, Ctrl+Shift+H heading (cycles), Ctrl+Shift+Q quote, Ctrl+Shift+U bullet list, Ctrl+Shift+O numbered list, Ctrl+Shift+T task item, Ctrl+Shift+I image, Ctrl+Space complete word. `VK_OEM_3` and `` Ord('`') `` are both handled for inline code (the key code depends on the widgetset layout).
- Context menu (`EditorPopup`, built in `FormCreate`): Undo, the clipboard block, Select All, a `Format` submenu (bold/italic/strike/code, heading, code block, quote, the three list kinds), an `Insert` submenu (link, image, table, horizontal rule) and `Complete word` — each with its shortcut shown, all dispatching through the same enum.
- The format bar is a `TPanel` (`alTop`, hidden by default) of flat `TSpeedButton`s with ASCII captions (`B`, `I`, `S`, `<>`, ```` ``` ````, `H`, `>`, `*`, `1.`, `[]`, `Link`, `Image`, `Table`, `---`, `Word`), built once at run time by `BuildFormatBar` (`FFormatButtons` keeps them) and never in the `.lfm`. `Editor → Formatting bar` (`Tag` 5) or the *Application* tab toggles `FEditorOpts.ShowFormatBar`; the bar is `alTop`, so the align pass simply hands the tree/editor/viewer the rest and `ArrangePanes` is untouched. `ApplyChromeColors` paints the panel (`Bg`/`Fg`) and `ApplyFormatBarTheme` pushes the font colour into the buttons; `ApplyEditorOptions` is what shows/hides it.
- Smart Enter (`[Editor] smartenter`, default **on** — `FormCreate` seeds the record before `LoadINI`, so a settings.ini without the key keeps it): only the plain Enter and only at the end of the line (`mdNone` otherwise; splitting mid-line stays the editor's job). `MdContinuation` reports `mdContinue` with the marker of a list item (`- `, `* `, `+ `, `1. ` → the next number, task items `- [ ] `) or a quote (`> `, nested markers included) with the *indent excluded* — the editor's own `cCommand_KeyEnter` supplies the auto-indent, and the prefix is inserted right after it, both in one undo group; `mdExitList` on an item that has no text removes the marker (`[lineStart, caret)`) **without** a newline, which is how an empty item ends the list instead of starting another. A line inside a fenced block does not continue anything: the handler counts the fence lines above the caret and passes the parity to `MdContinuation`, so a `- ` inside ```` ``` ```` stays text.
- Word completion is in-place, no popup: `Ctrl+Space` completes the word before the caret from the document's own words (`MdCollectWords`, minimum length 2, case-insensitive, sorted, numbers dropped), and pressing it again cycles to the next candidate, wrapping at the end; the candidate replaces the **whole word** around the caret, so a caret in the middle of `alpha` and a candidate `alphabet` cannot leave a tail behind, and the typed prefix is never offered as its own completion. The word list is scanned synchronously on the first press (ATSynEdit_Cmp would need ATListbox/ATFlatControls, which this project does not carry; a focus-stealing popup was not wanted either), and the cycling state is dropped as soon as the selection is not a caret or the prefix changed.
- `mddialogs.pas`: link, image and table dialogs are built at run time (no `.lfm`, like the Options dialog), painted by a record that mirrors `ApplyChromeColors`, and OK validates through a `TMdDialogHelper` (a `TComponent` owned by the dialog) that sets `ModalResult := mrNone` to keep the dialog open on an empty link target or a bad image source. The image dialog accepts an http(s)/`data:` URL as well as a file (absolute or relative to the document's folder), shows a thumbnail, and its "copy into assets/" checkbox (only when the document is saved; the answer is remembered for the session in `FImageCopyToAssets`) copies the picked file into `<doc folder>/assets/` — a numbered name on a collision, a same-name/same-size file is reused, the copy is only attempted when the source really exists — and stores the forward-slash relative path `assets/<file>`, which both preview backends resolve. The table dialog takes 1..12 columns and 0..50 rows.
- Auto-pairs are unchanged on purpose: `*` is **not** added to `OptAutoPairChars` (typing `*` would then produce `**` and make `*x*` awkward); emphasis comes from the toggles/shortcuts.
- Verified: the engine with 80 headless assertions (`/tmp`, no LCL, not in the repo) over every transform, its undo/unwrap/edge cases included; the app side with a temporary in-process self-test that drove the *real* handlers (`BCEditor1KeyDown` and `MdExecute`) with a document — Ctrl+B and bold on a word, italic over a selection, heading twice, a two-line bullet list, task toggle, code fence, Smart Enter on `- item` (continues), on an empty item (exits) and inside a fence (leaves the key alone), three Ctrl+Space presses (alpha → alphabet → wrap), the format-bar toggle with its menu check and ini value, and one undo step per command — all as expected; the three dialogs by screenshot (dark palette, values prefilled, thumbnail rendered); and `[Editor] formatbar`/`smartenter` written by `SaveINI` and read back (`formatbar=1` in a hand-edited ini showed the bar). **Not verified: a real click on a bar button, a menu item or a dialog's OK/Cancel, and the assets copy itself** — X input does not reach the Qt window on this box (XWayland, no WM), so the handlers were called in-process instead; Windows/IE and GTK2 likewise stay uncompiled.

## Editor options (`mdoptions.pas`, *Editor → Options...* / *Preferences → Options...*)

- One record is the single source of truth: `TEditorOptions` (every persisted ATSynEdit option, enums as ordinals, plus the font and the two markdown-editing switches, `ShowFormatBar`/`SmartEnter`, which are not ATSynEdit properties) and `TMdAppOptions` (theme, syntax, CSS, sync, remote images, preview backend, engine, zoom, MRU count). `CaptureEditorOptions` seeds the record from the live editor; `LoadEditorOptions` then overrides each field with `ini.ReadBool/ReadInteger('Editor', key, <the captured value>)`, so a `settings.ini` from an older build — or one with a key deleted — keeps ATSynEdit's own default instead of a value invented here; `ApplyEditorOptions` clamps ordinals and bounds (an ini from a build with a longer enum must not index past the end), shows/hides the format bar from `ShowFormatBar`, and is the **only** code that writes these properties; `SaveEditorOptions` writes them all to `[Editor]`. `LoadINI` calls Load, `FormCreate` calls Apply right after it, `SaveINI` calls Save.
- The window is built at run time (`TfmOptions` in `mdoptions.pas`, no `.lfm` for it): seven tabs — *View*, *Gutter and ruler*, *Minimap and unprinted*, *Keys and indents*, *Mouse and carets*, *Files and undo*, *Application* — each in a `TScrollBox`, with `AddCheck`/`AddSpin`/`AddCombo`/`AddMappedCombo`/`AddEdit` helpers that record the `PBoolean`/`PInteger` of the record field they edit, so `Commit` (only when `ShowModal = mrOk`) writes every control back without a second name list to keep in sync. The *preview backend* and *engine* combos are mapped: their item order is not the stored id (preview 1/2/3, engine 1..7 with gaps), so the id travels in `Items.Objects` and `Commit` reads it back.
- `BuildPreviewList`/`BuildEngineList` (main unit) list only what this build can use: IE and the five JavaScript engines are `{$IFDEF MSWINDOWS}` — off Windows the JS engines fall through to the native path, so offering them would be a pick that changes nothing. `mnuOptionsClick` snapshots the app axes into `TMdAppOptions`, shows the dialog, and applies in a fixed order: editor options, MRU trim, syntax, theme/CSS/editor font (`ApplyTheme(True)` re-renders with the current engine; the previews' code font is the editor's), backend/engine (`LoadEngine` + `UpdateResult` + `ApplyViewMode`), zoom (`TrackBar1.Position` + `TrackBar1Change`), sync (`tmrScrollSyncer`, plus one `SyncEditorToPreview` when it is switched on, like `Synceditwithpreview1Click`), remote images (`ApplyRemoteImagesSetting(True)`, so an image refused under the old setting is retried), and `SaveINI` last. The *Application* tab also picks the editor font (the `FontDialog1` path of `Editor → Font...`) and the MRU count; *Enable Custom Style* is `mnuCSS`, so the tab and the Preferences menu cannot disagree.

## Editor

- The syntax switch is real: `ApplySyntaxEnabled` attaches or detaches the EControl lexer (`Adapter.Lexer := LexerForCurrentFile`, `nil` = "Enable Syntax highlighter" off, which is what removes token colors, folding and the parse on keypress), and `LexerForCurrentFile` falls back to the Markdown analyzer for an untitled buffer. **The adapter only learns about the text through editor change events**, and neither `LoadFromFile(fn, [])` nor a lexer attached after the fact raises one: both `ApplySyntaxEnabled` and the open handler call `BCEditor1.DoEventChange(0, False)` — the step the reference demo (`app/demo_adapter_econtrol`) does with `ed.DoEventChange(0)`. Without it the editor stayed plain (palette applied, tokens not) until the first keystroke, which is the "highlighting only starts when I type" symptom. `AdapterParseDone` returns early when `Adapter.Lexer = nil`: there is no parse to fill anything from and `TreeFill` needs a client.
- `BCEditor1: TATSynEdit` used directly (the old `TBCEditor` subclass with Win32 `EM_*`/`user32` hacks is gone). Selection/clipboard/undo go through `DoCommand(cmd, TATCommandInvoke.MenuMain)` from `ATSynEdit_Commands` (qualify the enum; plain `MenuMain` doesn't resolve). No `OnDblClick`/`SetParent` on `TATSynEdit` — use `Parent :=`, `OnClickDouble`, `Carets[0].PosX/PosY/EndX/EndY` (0-based), `OffsetToCaretPos` (0-based offsets), `Strings.Count`.
- Editor context menu is a runtime `TPopupMenu` (`EditorPopup`, built in `FormCreate`); the editor has no default popup. It also carries the markdown `Format`/`Insert` submenus and `Complete word`, all of them `MdCommandClick` (see *Markdown editing* above).
- Find dialog works on 0-based offsets (`FSelPos = -1` = find first), selection set via caret fields + `DoShowPos`.
- The `Tree` panel is the table of contents, and MDPad fills it (`UpdateTOC`), because EControl cannot: `lib.lxl`'s Markdown lexer has no tree rules, so `TreeFill` produced nothing for a markdown document and the tree was empty (the adapter is kept for the highlighting; `AdapterParseDone` fills the tree with `TreeFill` only when the lexer is not Markdown — so C/PHP/Bash files keep EControl's own tree — and `OnParseBegin` is not wired, since it clears the tree on every parse). `UpdateTOC` runs after a render (`SyncUpdateUI`, from the engine's heading list) and on a document/engine/backend switch (`LoadEngine`), skips the rebuild when the headings are unchanged (`TocMatchesHeaders`, so typing does not tear the tree down), nests entries by `THeaderItem.Level` (1–6) and gives each node a `TATRangeInCodeTree` over its section (heading line → line before the next heading). That type is what keeps `EditorChangeCaretPos` → `CodetreeSelectItemForPosition` selecting the entry the caret is in, and what `TreeClick` (`Tree.OnClick`, `Tree.Selected`) reads: a click is `JumpToSourceLine(PosBegin.Y)`, which moves the caret *and* the editor's top line and hands the line to the active backend through `SyncEditorToPreview` — so a heading lands at the top of both panes, with or without the sync tick. Node data is freed by MDPad (`ClearTOC`), not by LCL. The canvas backend has no worker to report headings, so `AdoptCanvasOutline` takes them off the viewer's own outline (`PreviewMd4D.Toc`, i.e. Markdown4D's `TMarkdownToc`), through the same `HeadersFromOutline` conversion the `mdMARKDOWN4D` worker uses. It runs wherever that viewer's `SetText` does (`UpdateResult`, `LoadEngine`) *and* from the sync tick whenever `PreviewMd4D.LayoutCount` has moved past the layout the table came from (`FCanvasLayoutCount`): the viewer parses only once it has a viewport width, which a backend switch gives it after the render, so the outline read at that moment is empty — without the tick check the tree would stay empty until an edit. The TOC is filled for every backend and engine. Both fills are skipped while the tree is hidden (*View → Table of contents*, see *Architecture*): the contents are rebuilt once when it is shown again, and `UpdateTOC`'s `TocMatchesHeaders` fast path keeps the nodes when the headings did not change meanwhile.
- Scroll-sync is two-way, exact and content-aware (`tmrScrollSyncer`, 125 ms): both panes remember where they were left (`FSyncEditorLine`/`FSyncCaretLine`/`FSyncPreviewPos`; `FSyncEditorLine = -1` = *editor is authoritative*) and whichever one moved since the last tick drives the other, so the two cannot fight. **Editor → preview** maps the editor's top line (`TATSynEdit.LineTop` — a *logical* line, `FWrapInfo[N].NLineIndex`, not a wrap row) and only pulls the caret line in when it would fall outside the view (`TMarkdownPreviewScroll.OffsetShowingLine`, reused from the Markdown4D package rather than re-derived); the canvas backend asks `SourceLineToScrollOffset` (exact, images and code blocks included), the HTML backend interpolates between heading anchors. **Preview → editor** inverts the same maps (`ScrollOffsetToSourceLine`, `HtmlYToLine`). No average height is ever used. The HTML anchor table (`BuildHtmlAnchors`) is built from the headings the engine rendered (`FHeaders`, handed over by the worker in `SyncUpdateUI` via `AdoptHeaders`) plus the document ends, taking each heading's Y from the viewer's own name→section map (`PreviewHtml.SectionList.IDNameList` / `TIDObject.YPosition`, the map an in-page link jump uses) — a heading the engine left unnamed (`Id = ''`) is skipped — and is invalidated on re-render, resize, zoom and backend switch; a document without headings (or a JS engine, which stays one-way) keeps the old line-ratio scroll. Status bar via `OnChangeCaretPos` → `UpdateCaretStatus`.

## Platform quirks that bite

- THtmlViewer defines `NoMetaFile` outside Windows (`htmlcons.inc`): **no `Print`/`PrintPreview` methods on Linux**. Printing uses `PrintHtmlViewer` (paginated `MakeBitmap` via `TPrinter`); `PrintPreview1` is disabled unless `UsingIE` (`ApplyViewMode`). Zoom = `DefFontSize` scaling (`PreviewBaseFontSize`), not optical zoom. Markdown4D has its own path (`PrintMarkdown4D`, same page-bitmap trick over a `TMarkdownLclPainter`, with `Painter.OriginY` naming the document Y mapped to the page top and the render viewport given in *document* coordinates — see `TMarkdownViewer.Paint`).
- Links in THtmlViewer: `OnHotSpotClick` → `OpenURL` for http(s), in-page anchors left alone. Elsewhere `OpenURL`/`OpenDocument` (LCLIntf) replace `ShellExecute`.
- Canvas backend painting: Markdown4D renders its visible slice into a buffer and blits it at the scroll offset only on the widgetsets that scroll the canvas itself (GTK paints on the scrolled `GtkLayout`); on Qt (and Win32) the canvas origin is the widget's top-left, so the slice goes at 0 (`CanvasScrollsWithContent` in the library's `Markdown4D.Lcl.Viewer`/`Editor`). Blitting at `ScrollOffset` on Qt lands the slice off the bottom and leaves everything above it as the widgetset's background — the "gray band" the canvas pane showed whenever the sync scrolled it. Fixes belong in the library, not here.
## Preview conversion (worker thread)

- `UpdateResult` → `PerformConversion` spawns `TConversionThread` (MyWiki `TMarkdownConverter`); UI update happens in `SyncUpdateUI`. Stale results are ignored via `FCurrentRequestID`; previous worker gets `Terminate` (checked before sync). `LastPreviewBody` (used by Export HTML) is set in `SyncUpdateUI`, not in `UpdateResult`.
- Thread lifetime rules (all learned from real GPFs): use blocking `Synchronize`, NEVER `Queue`, with `FreeOnTerminate` (queued calls can run after self-free → intermittent GPF).
